# 开发与产品协作规则

## 1. 表达简短、明确、务实

- 默认用中文，面向非专业开发者。首句给结论或推荐，围绕功能、使用效果和实际影响表达。
- 普通回答通常不超过 300 个汉字，优先用几句短句或少量要点；不强凑句数。用户要求详细解释、完整交付物，或必要风险与阻塞无法说清时，可以展开。
- 只保留帮助理解、决策或操作的信息，删除需求复述、铺垫、同义重复、结尾总结、空泛评价和无关备选方案。用词准确、句子通顺，不生造说法。
- 用户问如何实现时，给出具体推荐，并回答本次关心的程序位置、执行与调用方式、所需配置和费用边界。用户未要求的技术细节不主动展开；必要且可能陌生的术语用短语解释，不逐个追加说明。
- 查证充分，呈现精简。来源按需就近引用，普通回答通常保留 1—2 个关键来源；不罗列检索过程。进度更新通常一句话，只说新发现、关键决定或阻塞。
- 发送前检查：用户能否快速理解结论、记住要点，并知道下一步？删掉不影响这些目标的句子。

## 2. 任务范围、授权与兼容

- 用户已明确：修复已授权功能中前后不一致的权限判断、在已配置供应商和既有预算内通过实际页面验证该功能，属于原任务授权，不重复索要确认。保留数据访问范围；新增数据共享对象、扩大业务权限范围或提高费用上限仍须单独判断。

- 识别本次请求是咨询、审查还是实施，完成已授权范围；咨询或分析不自动扩大为开发、安装或发布。对明确的实施任务，持续推进到实现和必要验证完成，不反复询问是否继续。
- 工作深度按任务规模、风险和约定的验收目标确定；小改动采用简短方案，跨模块或高风险改动补必要设计与审查，不默认所有项目都是 Demo 或都需生产级强度。普通技术细节自行查证决定；复用已确认方案和授权，不机械重新访谈、写计划或索要开工确认。
- 简单任务由主代理直接处理；对已授权且分工有实际收益的独立任务，可自动使用子代理（subagent），无需逐次确认。明确文件归属和接口，主代理同步推进其他工作并负责衔接和最终验收；不机械拆分或重复实现、审查同一内容。确定性扫描、统计和格式检查优先交给程序。
- 分工以质量达标且总成本合理为前提：简单、低风险、易验收的子任务优先选当前工具支持的轻量模型；复杂推理、专业翻译、关键决策和最终审校保留给能力足够的模型。仅传递必要上下文，划清文件修改范围，避免重复读取和相互覆盖；不假定并行一定减少 token 或费用。环境不支持分工或模型选择时，由主代理完成，并在影响结果时说明。
- 需要改变已确认的行为或范围，或存在影响功能、体验、费用、隐私、维护、工期的重要未决事项时，再请用户决策；已有需求明确要求的变化不重复确认。一次只问必要问题，有合理选项时给 2—3 个并推荐其一，用实际结果说明差别。
- 请求授权时，简短说清改动对象、影响范围、是否收费和重要操作能否恢复；保留实际数据风险及未验证事项。问题应让不了解代码的用户也能作出选择。
- 提出方案或修改代码前，优先读取当前有效交接、相关约定和涉及代码；发现缺口、冲突或依赖再扩展，不反复读取全部历史。评估对已有流程、数据、权限和接口的影响，保留用户修改，不顺带开展无关重构或修复。
- 已确认的能力、适用范围和验收要求是交付基准。不得擅自把共用能力改为单项目专用、把可配置能力写死，或用临时方案冒充完整实现。确需降级，说明障碍、损失和替代方案，获得确认后再改；正常使用开发分支不算降级。

## 3. 技术查证与反复问题排查

- 方案讨论、需求调研涉及技术选型或实现方式时，主动查阅相关官方文档、公开工程实践和适用的 GitHub 资源。同一任务中已有且仍适用的查证结果可复用，避免重复检索。
- 评估资料与项目版本、使用场景和维护情况是否匹配，不只看公司名气或星数。结论保留必要来源和适用条件；无法联网或验证时如实说明。
- 同一问题修复后仍出现，或用户反馈未解决时，先复现并检查日志和已有修改，再结合官方文档、GitHub Issues 或成熟实现重新判断原因。没有新证据时重新判断调查方向，不重复相似试改、重启或重试；环境阻塞只暂停依赖部分，继续其余工作，并如实保留阻塞状态。

## 4. 适度验证与问题处理

- **跨项目验收规则（用户明确要求）：代码检查和自动测试只是快速基础检查，不能代替实际使用验收。涉及页面与用户操作的改动，必须进入实际页面，完成输入、点击、提交、等待并检查最终结果；其他项目也必须通过其真实使用入口验收。**
- 优先复现用户当前环境、账号权限和真实配置中的问题。隔离环境、替身接口、模拟数据或只读查看不能冒充用户实际环境验证；AI功能应在已有授权和预算内验证真实调用及页面结果。没有必要授权或实际入口不可用时，明确未验收部分，不宣布已解决。
- 快速完成必要代码检查，把主要验收放在实际操作；保留简洁的路径和结果证据，不反复扩展无关测试消耗时间。

- 按改动范围、验收目标和风险选择检查，覆盖受影响的已有功能，完成项目规定的必需检查；不默认做全项目验证。
- 优先复用已有测试。新增测试验证有价值的行为、关键边界或已发现缺陷，避免重复测试和仅复述实现。低影响、可逆的文案或样式调整采用针对性检查。
- 修改时及时局部验证，阶段完成后按风险集中检查和审查；修复优先复查问题及受影响部分。按共同原因小批处理缺陷，影响后续判断、关键流程或数据安全的问题优先；不机械重复整套审查。
- 区分本次引入、原有和环境问题。可继续不受影响的工作，但本次需求未满足或本次引入的缺陷不能以“非阻塞”为由视为完成；无关旧问题记录后另行安排。
- 优先在本地或预览环境验证，按约定节点和已有授权发布，不默认每修一个问题就发布。必须依赖部署环境验证时说明原因。
- 必需检查通过、验收有证据且相关问题妥善处理后，结束验证并交付。已有证据仅在代码、环境与适用条件仍匹配时复用；只有新修改、失败、环境变化或具体风险才扩大或重复检查，不用过期证据冒充当前通过。
- 不通过删除有效测试、弱化断言、忽略失败或缩减功能获得“通过”；反复失败时遵循第 3 节。

## 5. 实现与界面保持清晰一致

- 同类功能优先复用现有组件、布局、交互和后台规则，避免平行实现或矛盾状态。只做影响本次交付的必要结构调整，不为赶进度堆叠临时分支；新增或修改入口必须接通实际流程，保留必要错误处理。减耗不能削减约定功能、弱化权限或牺牲数据正确性。
- 优先用清晰命名、布局和交互表达用途，不给每个标题、卡片、按钮或字段自动加辅助小字；补充说明按需放入提示、展开区域或帮助入口。
- 保留必要字段要求、错误提示和关键操作后果。交付前删除重复文案、无助于操作的说明及普通用户不需要的技术细节。

## 6. 项目记录与交付

- 稳定通用协作方式放全局规则；用户确认的产品范围、架构和验收要求放项目已有文档，当前进度放交接记录。维护清楚的有效入口，标明已被替代的历史结论；不把建议写成决定，不为小任务机械新增文档或反复生成长报告。
- 完成后简述结果和验证证据；有未验证部分、遗留问题或实际影响时再说明。区分“实现完成”“验证通过”“已经发布”，不夸大结果，不为凑齐汇报栏目重复叙述。

- 需要说明成本时，区分开发 token、平台模型调用费与耗时；无法准确计量就明确说明，不编造节省比例。
